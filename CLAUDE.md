# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Otterball v2 is a Django + Discord bot sports prediction platform (originally built around the FIFA World Cup, now also running NFL pools). Users submit match predictions via native Discord polls; a Celery cluster ingests match data from the FIFA API, computes points, and a bot posts/reconciles polls and a live leaderboard in Discord. The Django web side is intentionally thin: `/admin/` (data management), `/media/` (team logos), and four read-only public pages in `sports/views.py` — a season's upcoming fixtures (`/`), its knockout bracket (`/seasons/<id>/bracket/`), its pool standings (`/seasons/<id>/leaderboard/`) and its season stats (`/seasons/<id>/stats/`). Nothing on the web side writes: predictions are made in Discord and only rendered here. `predictions/views.py`, `users/views.py` and `discord_bot/views.py` are still empty stubs.

## Commands

Package management is via `uv` (Astral). Python 3.14+ required.

```bash
uv sync                                    # install deps (--frozen --no-dev in production, see Dockerfile)
uv run python manage.py runserver          # run the Django admin/web app
uv run python manage.py runbot             # run the Discord bot (discord.py, fully async against Django's async ORM)
uv run celery -A otterball_v2 worker --loglevel=info   # run the Celery worker
uv run celery -A otterball_v2 beat --loglevel=info     # run Celery Beat (scheduler)

uv run python manage.py test               # run the full test suite
uv run python manage.py test sports        # run tests for a single app
uv run python manage.py test sports.tests.SomeTestCase.test_something  # run a single test

uv run python manage.py makemigrations --check   # CI/pre-commit checks for missing migrations (otterball_v2/tests.py enforces this in-suite too)
uv run python manage.py migrate

uv run black .
uv run isort .
uv run manage.py test   # also runs automatically as a local pre-commit hook (django-test)

uv run python manage.py sync_fifa_infra --sync-teams --sync-competitions ...   # FIFA backfills, one flag per step
uv run python manage.py sync_nfl_infra                       # NFL: full setup for the current season (skeleton + teams + schedule)
uv run python manage.py sync_nfl_infra --season 2026 --sync-upcoming-matches --lookahead-days 25
uv run python manage.py sync_nfl_infra --sync-live-matches   # pull status/scores for matches that are live or already due

uv run python manage.py create_pool --name "NFL 2026" --sport AMERICAN_FOOTBALL --year 2026   # pool + config + stage rules (idempotent)
uv run python manage.py check_pool                           # is a pool actually ready? exits non-zero on FAIL

uv run python manage.py prune_team_logos                      # report team logo files no Team row points at
uv run python manage.py prune_team_logos --delete            # actually remove them

uv run python manage.py export_db [output.tar.gz]     # full backup bundle: DB (natural keys, skips contenttypes/permissions/sessions/celery results) + MEDIA_ROOT
uv run python manage.py export_db out.json.gz --no-media        # DB only, as a plain fixture
uv run python manage.py import_db backups/foo.tar.gz --flush    # restore a bundle; --flush wipes existing rows first to avoid PK conflicts
```

Local Docker stack: `docker compose up -d --build` (services: `web`, `bot`, `worker`, `beat`, `db` (Postgres 18), `valkey` (Redis-compatible cache/broker)). All four app services (`web`, `bot`, `worker`, `beat`) build from the same image/Dockerfile and just run different commands — keep that in mind when a change needs to reach all of them.

Pre-commit hooks (`.pre-commit-config.yaml`) run pyupgrade, django-upgrade, yamlfix, black, isort, `uv lock`/`uv sync`, the full Django test suite, and gitleaks — expect commits to be slow/blocked if these fail. Formatting: black/isort with `line_length = 118`.

## Architecture

Four Django apps, each with a distinct responsibility:

- **`sports`** — the sport data domain: `Competition` → `Season` → `Stage` → `Match`, plus `Team`. Every one of these has a parallel `*Mapping` model (`CompetitionMapping`, `SeasonMapping`, `StageMapping`, `TeamMapping`, `MatchMapping`) that links a local row to an external provider's ID (`SportsProvider.FIFA` for soccer; `SportsProvider.ESPN` and `SportsProvider.NFLVERSE` for the NFL, which is deliberately dual-sourced). This mapping-table pattern is how `sports/services/ingestion.py` upserts data idempotently from `sports/integrations/fifa.py` (the FIFA API client) without duplicating rows — always look up/create via the mapping table, not by guessing a match on name/date. `sports/integrations/fifa.py`'s pydantic schemas model the FIFA Digital Core Platform API, documented at `https://api.fifa.com/ApiFdcpSwagger/docs/v1` (Swagger 2.0 JSON, no auth required, ~260 paths) — treat that as the ground truth over the schema code when in doubt, since field aliases here are hand-transcribed and have drifted from the real API before (British-vs-American spelling, single-vs-double `s`, missing fields entirely — see `sports/tests/__init__.py::RealFifaApiResponseTests`). `sports/integrations/espn.py` is the NFL counterpart and spans two ESPN hosts on purpose: `sports.core.api.espn.com` for the season skeleton and schedule (its payloads nest entities as `{"$ref": ...}` links, and the ids we need are parsed out of those URLs by `_ref_segment` rather than fetched — chasing them would cost four extra requests per game) and `site.web.api.espn.com/apis/fantasy/v2/.../games` for status + scores of a whole date range in one request. A core `Event.id` **is** the scoreboard's `competitionId`, so a single `MatchMapping` serves both and no fuzzy matching is needed. Note `site.api.espn.com` — the host the old Otterball-NFL bot used — now returns 403 (Akamai), so don't reach for it. Neither ESPN API is documented; `sports/tests/test_espn.py::RealEspnApiResponseTests` pins the keys ingestion depends on (it asserts *required keys are still present* rather than FIFA's stricter *zero unmapped keys*, since ESPN ships far more per payload than is worth modelling).
`sports/integrations/nflverse.py` is the NFL's second provider: one CSV asset on a GitHub release (`nflverse-data/releases/download/schedules/games.csv`, no auth), read with stdlib `csv` rather than through `nfl_data_py` — the *package* pins numpy/pandas and stops at Python 3.12, but the *data* is just a file. It covers the schedule and **final** results back to 1999 and is a batch export, so it never carries in-progress state; ESPN stays the live source. Its `game_type` column already uses `REG`/`WC`/`DIV`/`CON`/`SB`, matching `NFL_STAGE_BLUEPRINTS`, and its `espn` column carries the matching ESPN event id for every row (verified 100% for 2025 and 2026) — a free cross-reference, which is why `ingest_nflverse_nfl_matches` attaches **both** mappings and adopts an existing ESPN-ingested match rather than duplicating it.
- **`predictions`** — `PredictionPool` (a competition instance users play in) → `PoolConfiguration` (when/how polls get created) and `PoolStageRule` (points per correct pick, keyed by stage, with a `stage=None` row as the pool-wide fallback, and `3` as the final hardcoded fallback). `Prediction` ties a `User` + `Match` + `PredictionPool` to a predicted `MatchOutcome`, and knows how to score itself (`update_points`/`aupdate_points`, sync and async variants — keep both in sync if you touch the scoring logic). `PredictionPool.aget_leaderboard()` implements Standard Competition Ranking (1-2-2-4) over **points, then hit rate** — points alone reward turning up as much as being right, so two players level on points are separated by the share of their picks that scored, and a tie now means level on both. `aget_user_with_points` annotates `pool_prediction_count`, `pool_correct_count` and `pool_hit_rate` (the unrounded ratio the DB orders by) onto each user; all three aggregates walk the same `predictions` relation through `filter=`, so they share one join and become FILTER clauses instead of multiplying each other's rows. The ranking compares `pool_hit_rate`, **not** the rounded percentage the surfaces display, so two rows can show the same percent and still be ordered.
- **`discord_bot`** — mirrors real Discord entities (`DiscordGuild`, `DiscordChannel`, `DiscordGuildRole`) plus app-specific state: `DiscordProfile` (1:1 with `users.User`), `ActiveMatchMessage` (the live link between a `Match`, a guild's poll message, and its status-message state), `DiscordGuildPool` (which pool is active in which guild/channel, with an optional notification role and pinned leaderboard message), `DiscordTeamEmoji` (custom emoji per team, used on poll buttons/leaderboard), and `PoolNotificationPreference` (per user *and* per pool opt-out of the pre-kickoff "you haven't voted" ping; reminders default to on, so an **absent row means notify** — read it through `aget_muted_user_ids`).
- **`users`** — thin `AbstractUser` subclass with a `uuid` field and an `is_discord_linked` convenience property.

### Data flow

1. **Ingestion** (`sports/tasks.py`, scheduled via Celery Beat / `django_celery_beat`): `sync_daily_infrastructure` walks competitions → national teams → seasons → stages → upcoming matches; `sync_live_games` polls only matches that are `LIVE` or `SCHEDULED` within 15 minutes of kickoff. All ingestion functions are async and live in `sports/services/ingestion.py`; they build local dicts as caches (`*_mapping_cache`) before looping to avoid N+1 queries against Postgres — follow this pattern rather than querying inside a loop. `sports/management/commands/sync_fifa_infra.py` exposes each step as a manual `--sync-*` CLI flag for backfills. The NFL path is `sync_nfl_infrastructure` (competition/season/rounds → teams → schedule) and `sync_nfl_live_games`, with `sync_nfl_infra.py` as the CLI equivalent. **Every `ingest_*` function is `async def`** — Celery tasks are sync, so they must wrap each call in `asyncio.run(...)` (via the `_run` helper in `sports/tasks.py`); calling one bare just builds a coroutine and silently discards it, which is exactly how `sync_daily_infrastructure`/`sync_live_games` were no-ops until this was fixed.
2. **Poll creation** (`discord_bot/cogs/poll_creation.py`, `PollCreationCog`): polls are posted **directly into the pool channel and pinned**, preceded by one announcement message that pings the notification role. They used to go into a per-batch thread; users disliked it, so that was removed — `ActiveMatchMessage.thread_id` is now nullable and only carries a value on rows from the threaded era, which is why every read goes through `ActiveMatchMessage.container_id` (`thread_id or channel_id`) and `discord_bot/utils.py::resolve_message_container` rather than either id directly. It is a self-adjusting `tasks.loop` that re-reads all active pools' configured `poll_creation_time`s from the DB every minute (`interval_sync_loop`) and reconfigures the actual posting loop's fire times (`poll_creation_loop`) accordingly — new/changed `PoolConfiguration` rows take effect without a bot restart. Poll answer ordering (draw included or not) is decided by `Stage.stage_type` via `DISCORD_POLL_ANSWER_ORDER_MAP` in `discord_bot/constants.py` — `GROUP` and `LEAGUE` (soccer groups, NFL regular season) get the 3-answer drawable ordering, `KNOCK_OUT` gets 2. A stage type absent from that map makes poll creation log an error and **skip the match entirely**, so any new stage type must be added there; `OTHER` is left out deliberately so an unclassified stage fails loudly.
3. **Vote capture** happens two ways and both must stay consistent: live, via `on_raw_poll_vote_add`/`_remove` in `discord_bot/cogs/poll_listener.py` (writes/deletes a `Prediction` per vote event), and in bulk via `discord_bot/services.py::sync_predictions_from_poll`, which re-derives every prediction from `message.poll.answers[].voters()` — this is the "tamper-proof" reconciliation pass mentioned in the README. It runs from two places: `ReconciliationCog.reconcile_active_polls()` on bot startup for every `ActiveMatchMessage` not yet finalized, and once more from `MatchTickerCog` at kickoff, right after the poll is ended (an ended poll cannot change any more, so that pass is final). It is a *full* re-derivation: votes retracted while the bot was offline are deleted, not just added/changed ones.
4. **Scoring**: `sports/signals.py` publishes a `MatchUpdatePayload` to Redis (`settings.REDIS_MATCH_UPDATE_TOPIC`) on every `Match` save; `predictions/signals.py`'s `receive_match_update` (fired via `transaction.on_commit`, only when a match transitions to `FINISHED`) recomputes points for every `Prediction` on that match using a pool/stage-keyed rules cache. `predictions/management/commands/update_points.py` is the equivalent manual/backfill sweep over `is_processed=False` predictions (or all, with `--all`).
5. **Leaderboard display** (`discord_bot/cogs/leaderboard_sync.py`): renders into a message it never creates (`PoolOnboardingCog` does that, see below), polls every 30s, diffs a fingerprint (leaderboard + rules tuple) against the last-rendered state per `DiscordGuildPool` to avoid needless Discord API calls, and edits a single pinned message. Above rank 10 it collapses remaining users into a "Plebs" field, splitting across multiple fields if the 1024-char Discord field limit would be exceeded ("Pleb-Splitting").
6. **Match status message** (`discord_bot/cogs/match_ticker.py`, `MatchTickerCog`, wired in since the threads were dropped): one message per poll, built with **Components V2** (`discord_bot/components.py::MatchStatusView`) and *edited in place* through `MatchMessageState` — `STARTING_SOON` (`PoolConfiguration.reminder_lead_minutes` before kickoff — per pool, `0` switches the reminder off — naming the role members who still have no pick) → `IN_PROGRESS` (live score) → `RESULT_POSTED` (final score plus everyone who called it). Never one message per state: editing keeps the channel readable and, more usefully, only the first post pings anyone. It is posted as a **reply to its own poll** (`fail_if_not_exists=False`, so a deleted poll cannot block it). The reminder tracks the poll live: `PollPredictionCog` dispatches a custom `prediction_change` event on every vote add/remove and `MatchTickerCog.on_prediction_change` re-renders, dropping a voter from the list or putting a retractor back. That only works because the missing-voter tuple is **part of the render fingerprint** — the score does not move while the reminder is up, so nothing else would register the change. Nobody re-added is notified: an edit never pings. Because the lead time is per pool, the 1-minute loop's query window is the **widest** configured lead (`_widest_reminder_window`) and each match then applies its own pool's (`areminder_window`, which queries by `pool_id` rather than walking `active_msg.pool` — a lazy relation access there would be a sync ORM call on the bot's event loop). Driven by that loop plus the Redis match-update topic for immediate live scores, and guarded by an in-memory `(state, home_score, away_score)` fingerprint so an unchanged match costs no API calls. The same pass closes the poll at kickoff (end → unpin → final vote sync → `is_poll_finalized`), which is what keeps pins under Discord's 50-per-channel ceiling.
7. **Components V2** is used for the status message only, and the constraints are not negotiable: a message carrying these components **cannot also carry a poll**, which is why the poll message itself stays a classic content+poll message and must never be converted. Setting the `IS_COMPONENTS_V2` flag is one-way ("once the message has been sent, the flag cannot be removed"), so every state of the status message is V2 — `_upsert_ticker` edits with `view=` and never has a content/embed to clear. Mentions still notify: *"pingable mentions … will ping and send notifications based on the value of the allowed mention object"*, so the pre-kickoff reminder works exactly as before and still honours its `AllowedMentions`. Budget is 40 components and 4000 characters of text per message, and a `Section` takes 1-3 children plus one accessory — which is why a team with no `logo_url` falls back to plain `TextDisplay`s instead of an accessory-less Section. The **Mute reminders** button is a `ui.DynamicItem` carrying its pool id in the custom_id (`otterball:mute:{pool_id}`), registered once via `add_dynamic_items` in `setup_hook`, so buttons posted before a restart keep working with nothing stored per message.
8. **Garbage cleanup** (`discord_bot/cogs/remove_garbage.py`): deletes Discord's auto-generated "poll results are in" *and* "X pinned a message" system messages, both live (`on_message`) and via a startup historical sweep, sharing one `_is_garbage` rule. Two filters keep it from moderating rooms it was never pointed at: the channel must be one the bot manages (`_is_managed_channel`), and a pin notice must be the bot's own. Discord authors a pin notice as *whoever pinned the message*, so that second one is just `message.author.id == bot.user.id` — a moderator pinning something in the pool channel keeps their notice. The sweep dedupes by container so a channel is not re-read once per match.

### Conventions worth knowing

- **A pool's first two messages are posted by `discord_bot/cogs/pool_onboarding.py`, not by the flow that creates the pool.** Standing a pool up happens in the admin's guided page or `manage.py create_pool` — i.e. in the `web` container, which has no Discord connection — so the `DiscordGuildPool` row *is* the signal: `PoolOnboardingCog`'s 1-minute loop posts the season's welcome message and then the leaderboard message into the channel, in that order, with no bot restart. Creating the leaderboard message used to live in `LeaderboardSyncCog.on_ready` (so a pool bound after startup got nothing until a restart, and the two posts could race into a new channel in either order); that cog now only renders into a message that exists and returns early when it does not. The welcome post is **edited in place** on later passes against an in-memory render fingerprint, for the same reason the match ticker is one edited message: a pool is created *before* its points per round are set, so the first render of "what a pick is worth" is the flat seeded default and would otherwise stay wrong in the channel forever — and an edit never pings, so correcting it does not ping the notification role a second time. It is deliberately **not pinned** (pins are capped at 50 per channel and the polls need them; the role ping is this post's delivery mechanism), and a *deleted* welcome is never reposted — that would ping a role about a season already under way, so `discord.NotFound` is taken as intentional and only cached to stop the refetch. `welcome_msg` on `DiscordGuildPool` is that record and `announce_welcome` is the intent - clearing the id with the flag on is how you ask for the opener again, and the flag's data migration turns it **off for every binding that already existed**, because applying its `True` default to the pools running right now would ping their roles about a new season on nothing but a deploy. The guided setup page offers it as *Announce the new season* and `create_pool` as `--no-welcome`.

- Django's `FileField.save()` **never overwrites** - on a name collision it appends a random suffix and writes a second file. `ingest_national_teams` used to re-download a logo whenever any unrelated metadata changed (the guard read `if logo_url and logo_url:` instead of `logo_changed`), so `media/team_logos/` accumulated one orphan per team: 1148 files for 574 teams. The guard is fixed in both the FIFA and NFL paths; `manage.py prune_team_logos` clears what it already wrote and reports rows pointing at a file that is gone.
- **`export_db` bundles the media tree, because the database dump alone cannot.** A `FileField` serializes as a *path* (`team_logos/43835_saudi-arabia.png`), never bytes, and `media/` lives in the `django_media` Docker volume - so a DB-only restore onto a fresh machine leaves all ~574 teams pointing at logos that are not there. A `.tar.gz` output produces a bundle (`data.json` + `media/`); a `.json*` output is DB-only and **refuses unless you pass `--no-media`**, since the old failure mode was silent. `import_db` sniffs the tar header rather than the filename (a `.json.gz` fixture is gzip too), so plain fixtures from before this change still restore. Media restore is additive on purpose - files already in `MEDIA_ROOT` that the bundle does not mention are left alone, so a restore can never be what loses a logo - and extraction uses `filter="data"` because a bundle is a file that travels between machines.
- **Both `post_save` receivers on `Match` skip `raw=True`.** A fixture load is a restore, not live match movement: `sports/signals.py` would otherwise broadcast a live-score message per restored match, and `predictions/signals.py` would re-score every restored `FINISHED` match, overwriting the dump's own point values with recomputed ones. `sports/signals.py`'s Redis publish is deferred to `transaction.on_commit`, i.e. *outside* the receiver's own `try/except`, so it also needs `robust=True` - without it an unreachable Redis propagates out of whatever wrote the match, which is exactly the state a machine being restored onto is in. `MatchTickerCog`'s 1-minute loop re-reads the match anyway, so a dropped publish costs latency, not correctness.
- `poll_creation_lookahead_days` (how many days of matches go into one poll batch) is capped at `MAX_POLL_LOOKAHEAD_DAYS = 32`, and that number is **Discord's maximum poll duration**, not a project preference — a poll runs from creation until its match kicks off, so a longer batch would ask Discord for a poll it refuses to open ("Number of hours the poll should be open for, up to 32 days"). It was 7 for a long time because that was Discord's original limit. The **default is still 7**: a week per batch is the cadence pools actually run on, and raising the cap deliberately did not touch existing rows.
- The bot needs the **privileged members intent** (`intents.members = True` in `discord_bot/bot.py`, plus "Server Members Intent" enabled in the Discord developer portal, or login fails outright). It is what makes a notification role's membership visible; without it `role.members` is empty and the pre-kickoff reminder cannot tell who has not voted, so it posts without names rather than failing.
- Who gets reminded is `notification role members − users with a prediction − users who muted that pool`. A role member with **no `DiscordProfile` has never voted anywhere and still counts as missing**, which is why the set is built from the role and not from the profile table. A first vote from someone with no `DiscordProfile` now creates one (`services.py::aget_or_create_user_id`, via `PollPredictionCog._aresolve_user_id`) rather than being dropped until the next full sync — without it a first-time voter stayed named on the very reminder they had just answered. Users mute themselves per pool with the `/notifications` slash command (`discord_bot/cogs/notification_prefs.py`), which infers the pool from the channel it is used in and only asks for the `pool` option in a guild running several, or with the **Mute reminders** button on the reminder itself. Both go through `services.py::aset_missing_vote_reminders` so they cannot disagree about what muting means.
- Async-first: the bot and ingestion code use Django's async ORM (`aget`, `acreate`, `aiterator`, `aupdate_or_create`, etc.) throughout since discord.py's event loop can't block on sync ORM calls. Management commands that need to call async ingestion code wrap it in `asyncio.run(...)`.
- Model methods that touch scoring (`Prediction.update_points`/`aupdate_points`) are duplicated in sync and async form intentionally — signals call the sync path, the bot/async commands call the async path.
- `ExternalMappingBase` is the abstract base for all `*Mapping` models (`provider` + `external_id`, unique together); new provider integrations should extend `SportsProvider` and follow the same mapping-table pattern rather than adding provider-specific fields to core models.
- `REDIS_URL` doubles as both the Django cache backend (`django_redis`) and, via `CELERY_BROKER_URL`, the Celery broker default — don't assume they're separate Redis instances unless `.env` overrides them.
- Discord IDs are stored as `BigIntegerField` primary keys (not Django auto-increment) across `discord_bot` models — always pass the real Discord snowflake as `id=`.
- **NFL rounds are modelled one `Stage` each, not one per week.** `NFL_STAGE_BLUEPRINTS` in `sports/constants.py` defines the five scoreable rounds — Regular Season (`LEAGUE`, level 0), Wild Card, Divisional, Conference Championship, Super Bowl (all `KNOCK_OUT`, levels 1-4) — so a pool sets points per round with five `PoolStageRule` rows, the same five knobs the old Otterball-NFL bot's `GameTypeScaling` had. `nfl_stage_key(season_type, week)` maps an ESPN event onto one, and returns `None` for preseason, the offseason, and **postseason week 4 (the Pro Bowl)**, which are filtered out of ingestion rather than turned into polls. `StageMapping.external_id` is `"{year}:{key}"`, e.g. `2026:SB`.
- The NFL regular season is the only round that offers a Draw poll answer, because it is the only one where a tie is possible. That is why its `stage_type` is `LEAGUE` and the playoff rounds are `KNOCK_OUT`.
- ESPN reports an unplayed game's score as `""` (empty string), not `null`. `ScoreboardCompetitor.parse_score` maps it to `None` — do not coerce it to `0`, or an unplayed game looks like a 0-0 draw and scores points.
- `ingest_espn_nfl_matches` owns kickoff/teams/stage only; `ingest_espn_nfl_live_matches` owns status and scores. Keep that split — the live path is what transitions a match to `FINISHED`, which is what fires the scoring signal, and a schedule re-run must never walk a finished match back to `SCHEDULED`.
- **nflverse and ESPN disagree on two team abbreviations**: nflverse says `LA`/`WAS`, ESPN says `LAR`/`WSH` (the other 30 match). `NFLVERSE_TO_ESPN_TEAM_ABBREVIATIONS` bridges them, and `ingest_nflverse_team_mappings` seeds a `TeamMapping` per team keyed by nflverse's abbreviation. Without it the Rams and Commanders never resolve and roughly two games a week are silently dropped — run the team sync before the nflverse sync on a fresh database, or every game is skipped as unmapped. Both syncs guard against this rather than failing quietly: the seeder logs an error if it ends up with fewer than `NFL_TEAM_COUNT` mappings, and the match ingest collects unresolved abbreviations and reports them **once** with a game count (`Unmapped nflverse team abbreviations: LA (17 games)`) instead of one near-identical line per game. Unmapped teams and missing stages are reported separately, because they need different fixes — the team sync vs the infrastructure sync.
- nflverse's `result` column is home-minus-away, so `0` means a tie — test `is not None`, never truthiness, or every tied game reads as unplayed. Likewise a blank score cell means "not played yet" and must stay `None`, not become `0`.
- **The rank-over-time chart is server-rendered SVG; script only adds the hover layer.** `sports/charts.py` computes the geometry and the template emits the lines, axes and end-of-line player labels, so the chart is complete with JavaScript off — `sports/static/sports/js/rank-chart.js` adds the crosshair and tooltip on top and reads the plot box off the SVG's own `.hover-target` rect rather than duplicating the coordinates. Names reaching the tooltip go through `escapeHtml` first — they are Discord display names, i.e. user-controlled, and the tooltip is built with `innerHTML` (Django's autoescaping covers the SVG labels, not this). Two traps it already fell into: a `fill` on the shared series class **beats** `.line { fill: none }` and turns every line into a filled blob (lines take `stroke`, only labels and dots take `fill`), and `element.hidden` is an *HTMLElement* property that silently does nothing on an SVG node — the attribute has to be moved with `setAttribute`/`removeAttribute`.
- **The chart's palette was validated, not chosen, and eight is its full length.** The categorical slots come from the dataviz skill's reference palette and were run through its validator against this site's own surfaces (`#ffffff` / `#1c1f27`) in both modes (lightness band, chroma floor, CVD separation, normal-vision separation, contrast). All eight pass the adjacent gates — worst CVD ΔE 9.1 light / 8.4 dark against a floor of 8, normal-vision 19.6 / 19.3 against 15 — which is why `CHART_HIGHLIGHTED` is 8 and not more: a ninth colour would have to be invented, and the ordering it slotted into would no longer be one the validator passed. The slot *ordering* is the colourblind-safety mechanism — do not re-pick one by eye, and re-run `validate_palette.py` on any change. Light mode's contrast check WARNs, which obligates relief: every line is directly labelled at its end and the chart ships a table view. Both are load-bearing, not decoration. `sports/tests/test_views.py::RankChartLayoutTests::test_every_colour_slot_is_defined_in_both_modes` fails if `CHART_HIGHLIGHTED` outruns the CSS, which would otherwise draw a line with no `stroke` at all — i.e. black.
- **The chart draws the whole field, and names only the leading ten.** It first drew only the top ten *by final rank*, which left visible holes in the rank axis: at 8 of the World Cup pool's 104 matches the player leading at the time finished outside that ten, so nothing sat on rank 1 and a reader cannot tell that from a bug. Everyone is drawn now — the unnamed rest as a 0.18-opacity band whose top edge is the leader at every match — and `RankChart.leaders` carries whoever held rank 1 after each match so the tooltip opens on them even when they are not one of the ten. Including every past leader instead was the obvious alternative and is not viable: 27 different players led that pool at some point. `sports/tests/test_views.py::StatsViewTests::test_something_is_always_drawn_on_rank_one` pins it.
- **Who the chart names is the reader's choice, and the picker is pure client work.** Every player is already drawn as their own `<polyline>`, so selecting one is a class swap, not a request — which is why `RankChart.payload` ships *all* series with their samples rather than the named ten, and why lines, labels and every swatch (including the table view's) carry `data-user`. The colour a player wears comes from their position in the **current selection**, not their final rank, so picking three mid-table rivals gives them slots 1-3; `CHART_HIGHLIGHTED` still caps how many carry one and the rest are context grey with their end-of-line label. Two traps: SVG paint order *is* document order, so a newly selected line has to be re-appended to `.lines` or it is drawn under the field band; and label spreading has to shrink its gap when the whole field is selected, or the bottom names walk off the plot. The picker ships with `hidden` and the module reveals it — its checkboxes submit nothing, so with script off the chart keeps the server's ten and no dead control is on the page.
- **The chart's height scales with the rank range, not the player count.** Early in a season a leader can sit 40th on one lucky pick; a fixed-height box then squashes the whole story into its top eighth. `ROW_HEIGHT` gives each rank ~12px (the label gap), which is also what keeps every end-of-line label sitting exactly on its own line instead of being nudged onto a neighbour's.
- **The pool-wide stats all come off one `build_consensus` pass.** `MatchConsensus` carries each scored match's vote counts, the majority pick (`None` when the vote is tied — a split pool has no consensus to attribute) and `points_if_right`. That last one is the **highest `points_awarded` on the match**, not a `PoolStageRule` lookup: if anyone called the match, their award *is* the stage's rate, which is what keeps the crowd's score from re-implementing the fallback chain in `Prediction.update_points`. It is 0 when nobody called it, which is exactly when it is never read. Built on top: `build_crowd_standing` (the majority pick scored as a player and placed among the real ones on the same points-then-accuracy pair the leaderboard ranks by), `build_streaks`, `build_contrarians` and `build_outcome_mix`. **Contrarians are ordered by how often they went against the crowd, not by how well it went** — sorting by rate puts whoever defied the majority twice and got both right on top, which says nothing.
- **`predictions/history.py` does the walk for both the chart and `export_point_history`.** It takes an ordered list of predictions rather than querying, so the async view and the sync command share one implementation. Its last entry **must** equal the live leaderboard — same `CompetitionRanker`, same points-then-accuracy comparison — and `predictions/tests.py::RankHistoryTests` pins the two together, because they are computed by completely different code (a Python walk vs. SQL aggregates).
- **`{# ... #}` does not span lines in a Django template.** Only the first line is stripped; the rest renders into the page as visible text. This escaped review three times here, so `sports/tests/test_views.py::TemplateSyntaxLeakTests` now asserts no page renders `{#`, `#}`, `{%` or `%}`. Use `{% comment %}` for anything multi-line.
- **The sync cogs (`guild_sync`, `channel_sync`, `role_sync`) are one-line handlers and had one-line bugs**, all of which failed invisibly because the cogs had no tests: `role_sync` looked the guild up in `DiscordGuildRole` (always missed, so new roles were never recorded), `channel_sync` wrote the guild's snowflake over the channel's own primary key (`"id"` instead of `"guild_id"`, so every new channel raised an IntegrityError), and `guild_sync` used `guild_id=` on models whose PK is `id` — moot only because the cog was never registered in `bot.py`. It is registered now, and **`on_guild_remove` deactivates rather than deletes**: `DiscordGuildPool` and `ActiveMatchMessage` both cascade off `DiscordGuild`, so deleting the row would take a pool's binding and every poll it ever posted with it, for what is usually a temporary removal.
- **`matches_needing_polls` excludes on `ActiveMatchMessage` alone.** It used to be `exclude(predictions__pool_id=..., active_messages__pool_id=...)`, and since both conditions had to hold to exclude a match, one with a poll but **no votes yet** was polled a second time on the next batch. Whether anyone has voted says nothing about whether a poll exists.
- **`services.aget_or_create_profile` is the only place a User is created from a Discord account.** `sync_predictions_from_poll` used to create them inline without the display-name collision fallback, so a second voter sharing a name raised `IntegrityError` and took the whole reconciliation pass down. The collision is now **checked for** rather than caught: catching only recovers under autocommit — inside a transaction the failed insert poisons the connection and the retry raises `TransactionManagementError`.
- **`MatchTickerCog.pubsub_loop`'s interval is a reconnect delay, not a poll.** It was `tasks.loop(count=1)`, so any error ended it permanently — and discord.py only auto-retries `OSError`, `GatewayNotFound`, `ConnectionClosed`, `aiohttp.ClientError` and `TimeoutError`, none of which a `redis.RedisError` is. One Redis blip meant no live scores until the bot restarted, and silently: the minute loop kept working, so the only symptom was updates arriving a minute late forever. It catches `RedisError`/`OSError` and returns so the loop re-subscribes, re-raises `CancelledError` so `cog_unload` still stops it, and closes both handles in a `finally`.
- **`LeaderboardSyncCog` walks `aget_leaderboard` once, not twice.** It used to iterate it for the change-detection fingerprint and again for rendering — two full queries every 30 seconds, and two places to keep in step. The rows are collected once and both steps read that list; the hit rate is part of the fingerprint, so a pick that changes someone's accuracy without changing anyone's points still redraws the message.
- **`/media/` is served by middleware, not by the URLconf.** `otterball_v2.middleware.WhiteNoiseWithMediaMiddleware` is WhiteNoise with `MEDIA_ROOT` added at `MEDIA_URL`; there is no reverse proxy in front of the `web` service (compose publishes gunicorn on 8000 directly), so nothing else would. It replaced `django.conf.urls.static.static()` in `otterball_v2/urls.py`, which returns `[]` when `DEBUG` is off — crests worked in development and 404ed in production, and the pages silently fell back to initials. Do not add a media route back to the URLconf: one code path for both environments is the fix, and the old split is exactly what hid the bug. **`WHITENOISE_AUTOREFRESH = True` is part of it, not a leftover from development** — WhiteNoise indexes files once at startup, and the *worker* container downloads crests into the `django_media` volume that the already-running `web` container serves from, so without it a newly ingested team's crest 404s until `web` restarts. `otterball_v2/tests.py::MediaServingTests` fails if either half is removed. The **bot** container needs the `django_media` volume for the same reason the web one does: `EmojiSyncCog` reads crest bytes off disk (`team.logo.open`) to upload them as application emoji, and a missing file lands in its `except Exception` and is only ever a log line.
- **The ingestion schedule is code, not an admin chore.** `sports/schedules.py` declares every `PeriodicTask` the ingestion needs — task, cadence, sport, and whether a pool of that sport breaks without it — and both `manage.py ensure_schedule` and `readiness._check_ingestion` read it, so the installer and the checker cannot disagree. `ensure_schedule` matches an existing row on its **dotted task name, not its label**: a hand-made row can be called anything ("Live Match Sync"), and matching on the label would add a second row scheduling the same task. It never touches a row it did not create unless `--reset` is passed.
- **Freshness is read from `PeriodicTask.last_run_at`, not from a task result.** `celery.backend_cleanup` deletes `TaskResult` rows after a day by default, so a *daily* task's last success keeps vanishing and would read as "never ran". The newest `TaskResult` is used only to notice that runs are *failing* — Beat happily keeps dispatching to a worker that throws every time, so `last_run_at` alone looks healthy. A task is called stale after `STALE_AFTER_INTERVALS` (3) missed cycles, with a 30-minute floor so a two-minute task is not reported stale after six minutes of a slow worker.
- **The ingestion catch-up lives on the worker, never on the bot.** `sports/catchup.py` hooks Celery's `worker_ready` and runs the overdue infrastructure syncs once, so a spell with Beat down does not leave a pool without fixtures. It belongs on the worker because the bot is one of four containers and restarts on every deploy — a crash-loop there would mean repeated full ingestion (the NFL infra sync alone is ~70 HTTP requests). **It must never write `PeriodicTask.last_run_at`**: only Beat writes that, so the data gets refreshed while `check_pool` and the admin's **Ready?** column go on reporting the schedule as stale, and a dead Beat stays visible. Do not "tidy" that by stamping it — the split is the whole design. Guarded three ways: only sports with an active pool, only tasks marked `catch_up` in `sports/schedules.py` (not the every-two-minute live syncs, where a one-shot settles nothing the next tick would not), and a cache lock so a rolling restart dispatches one round rather than one per worker. A task with **no** `PeriodicTask` row is deliberately left alone — that is a missing schedule for `ensure_schedule` to install, and running it here would paper over the failure readiness reports. Switch the whole thing off with `INGESTION_CATCHUP_ENABLED=0`.
- **The public views are async, and that is load-bearing.** Django serves a class-based view on its async path only when *every* handler is a coroutine (`View.view_is_async`), so `SeasonPageView` overrides `get` and not `get_context_data` — `get_context_data` is not on that path, and pages add their context in `aget_page_context` instead. A sync handler slipped into any of them silently drops it back onto the sync path; `sports/tests/test_views.py::AsyncViewTests` asserts the three stay async. Template rendering itself still happens in a sync thread (the base handler wraps `TemplateResponse.render` in `sync_to_async`), so a lazy relation in a template will not raise `SynchronousOnlyOperation` — it will just cost a query per row, which is why the querysets `select_related` everything the templates touch.
- **The public pages are season-scoped and pick their own default.** `/` resolves the season owning the next match to be played (falling back to the most recent match, so the off-season is not a blank page) rather than reading a flag, so nothing has to be marked "current" by hand. `sports/views.py::group_by_day` groups fixtures by *local* date via `timezone.localtime` — a 01:30 CEST kickoff is the previous day in the database, and a World Cup night session is exactly that case. The bracket renders one column per `StageType.KNOCK_OUT` stage ordered by `Stage.level` (which every ingestion path sets in playing order), and deliberately draws **no connecting lines**: the schema stores no bracket progression, so a line between two columns would be a guess that is wrong for any round not yet played. It is the one page that escapes the 1100px reading column — six World Cup rounds are ~1700px, so `base.html` has a `{% block wide %}` outside `.wrap` for it, and `.bracket`'s inline padding (`max(20px, calc((100% - 1100px) / 2))`) starts the first column level with the heading and then scrolls away. Discoverability of that scroll is carried by the **round rail**, a nav naming every round whether or not its column is on screen (a cut-off card only says something is broken); the right-edge fade is a bonus that only appears where `animation-timeline: scroll()` is supported, because a fade that cannot tell whether anything remains would sit over the Final for no reason. The prediction split on a match card offers a Draw segment iff the stage is in `DRAWABLE_STAGE_TYPES` (`sports/constants.py`), which mirrors what `DISCORD_POLL_ANSWER_ORDER_MAP` decides for the poll itself — `sports/tests/test_views.py::DrawableStageTypeTests` pins the two together. Finished matches carry a split too, with `VoteShare.is_correct` set on the outcome that happened: on a result the bar stops being a poll and becomes an answer key, so the ticked count is how many people called it. Nothing is marked on a **knockout tie** — the schema stores the level score, not who won on penalties.
- **The leaderboard page reads `PredictionPool.aget_leaderboard`, the same generator the bot's pinned message reads**, so the website and Discord cannot disagree about who is second — do not reimplement the 1-2-2-4 ranking for the web. It renders one table per pool of the season (several pools is the uncommon case, and a picker would hide one) and has no "Plebs" collapse, since a table has no 1024-character Discord field limit to work around. Names come from `users.User.display_name`, which prefers the Discord `global_name` for the same reason — it is the name people know each other by in the channel. That property reaches the profile through the reverse accessor rather than importing `discord_bot` (which depends on `users`, not the other way round), so any caller rendering more than one user must `select_related("discord_profile")` or it is a query per row; `_user_points_queryset` already does. **Hit rate** is `correct / picks`, rounded for display by `predictions.models.hit_rate_percent` — the single place that rounding happens, called by both the web table and the Discord embed (`**Name** (points · NN%)`), so a player cannot read two different numbers in the two places. It is also the ranking tiebreaker; see `aget_leaderboard` above. The **Correct** column is derived from `points_awarded > 0` — a `Prediction` records what was picked, never whether it matched — so a `PoolStageRule` awarding zero points for a round would hide a correct pick in it.
- **App-local `static/` directories are un-ignored explicitly.** `.gitignore` has to keep `static/` (it is `STATIC_ROOT`, i.e. collectstatic output) but that pattern matches at any depth, so `!*/static/` re-includes `sports/static/`, which is source. Production serves it through whitenoise after the `web` service's `collectstatic`.
- `sports/tests/fixtures/*.json` are genuine captured responses from the live FIFA API (World Cup 2026, `competition_id=17`, `season_id=285023`), fetched via `curl -A "Mozilla/5.0" "https://api.fifa.com/api/v3/..."`. `RealFifaApiResponseTests` in `sports/tests/__init__.py` parses them and asserts every JSON key maps to a model field — parsing success alone isn't enough, since pydantic's default `extra="ignore"` silently drops unmapped keys instead of erroring. Refresh these fixtures periodically (or when touching `fifa.py`'s schemas) to catch further drift from the real API.

## Starting a new pool

The bot is generic over sports; standing up a pool is one ingestion run plus one command.

```bash
# 1. Sport data: competition, season, rounds, teams (logos + colours), schedule.
uv run python manage.py sync_nfl_infra

# 2. The pool itself: PredictionPool + PoolConfiguration + one PoolStageRule per round.
uv run python manage.py create_pool --name "NFL 2026" --sport AMERICAN_FOOTBALL --year 2026 \
    --weekdays 2 --time 18:00 --lookahead 7 --reminder-lead 60 \
    --points "Regular Season=1,Wild Card=2,Divisional=3,Conference Championship=4,Super Bowl=5"

# 3. Start the bot once. ReconciliationCog creates the DiscordGuild/Channel/Role rows
#    and EmojiSyncCog registers a team emoji per logo. Leave it running: once step 4
#    binds the pool, PoolOnboardingCog posts the welcome message and the pinned
#    leaderboard within a minute.
uv run python manage.py runbot

# 4. Bind the pool to a guild + channel (now that step 3 has populated them).
uv run python manage.py create_pool --name "NFL 2026" --sport AMERICAN_FOOTBALL --year 2026 \
    --guild <guild_id> --channel <channel_id> --notification-role <role_id>

# 5. Confirm it is actually ready.
uv run python manage.py check_pool
```

Then schedule the ingestion — or rather, check that the deploy did. **Celery Beat is
database-driven** (`CELERY_BEAT_SCHEDULER = django_celery_beat.schedulers:DatabaseScheduler`), so a
task existing in `sports/tasks.py` does nothing until a `PeriodicTask` row exists for it. Those rows
are declared in `sports/schedules.py` and installed by `manage.py ensure_schedule`, which the `web`
container runs right after `migrate`:

```bash
uv run python manage.py ensure_schedule            # create any missing rows (idempotent)
uv run python manage.py ensure_schedule --dry-run  # report what is missing, change nothing
uv run python manage.py ensure_schedule --reset    # also put existing rows back to the declared cadence
```

A starting Celery worker also runs any overdue infrastructure sync once
(`sports/catchup.py`), so a spell with Beat down does not strand a pool. Set
`INGESTION_CATCHUP_ENABLED=0` to leave the schedule entirely to Beat.

For the NFL that means three rows:

| Task | Suggested cadence | Does |
|---|---|---|
| `sports.tasks.sync_nfl_infrastructure` | daily | season skeleton, teams, abbreviation bridge, schedule |
| `sports.tasks.sync_nfl_live_games` | every ~2 min | status + scores; this is what transitions a match to `FINISHED` and fires scoring |
| `sports.tasks.sync_nflverse_results` | a few times a day | independent backstop for finals, plus ESPN id cross-referencing |

`create_pool` is idempotent — re-running with the same `--name` and season updates rather than
duplicating, which is why steps 2 and 4 are the same command.

**The same flow has a guided page in the admin**: *Prediction pools → Start a new pool*
(`/admin/predictions/predictionpool/setup/`). It opens with the two prerequisites above (is sport
data ingested, has the bot connected), does steps 2 and 4 in one form, and finishes with the step-5
readiness report inline. Points per round are deliberately not on it — they depend on which season
is picked — so it hands you to the pool's own page, where `PoolStageRuleInline` already edits them.
The channel and role pickers are **filtered by the chosen guild in the browser**
(`predictions/static/predictions/js/pool_setup.js`, off a `data-guild` attribute that
`GuildScopedSelect` puts on every option) — no endpoint, no round trip. That is a convenience only:
the options stay labelled `Guild · name` so the unfiltered list is usable with scripting off, and
`PoolSetupForm.clean` re-checks the pairing server-side, which is what actually keeps a channel from
the wrong server out of the database.
The plain **Add prediction pool** button still exists and still leaves a pool with no schedule, no
scoring and nowhere to post, which is what the guided page is for.

Everything is still available piecemeal in `/admin/`: `PredictionPool` carries `PoolConfiguration`
and `PoolStageRule` as inlines and seeds missing rules on save, and `DiscordGuildPool` is where the
guild binding lives.

**The ordering in step 3 is a hard dependency, not a preference.** `DiscordGuild`, `DiscordChannel`
and `DiscordGuildRole` rows are only created by the bot's `ReconciliationCog` on `on_ready`, so
until the bot has connected once there is nothing to bind a pool to — the admin dropdowns are empty
and `create_pool --guild` refuses with a message saying so.

### Why check_pool exists

Almost every way a pool can be misconfigured is silent:

| Misconfiguration | Symptom without the check |
|---|---|
| No `PoolStageRule` rows | Every pick scores the hardcoded fallback of `3`; per-round scaling silently doesn't happen |
| Stage type missing from `DISCORD_POLL_ANSWER_ORDER_MAP` | Poll creation skips every match in that round |
| No `DiscordGuildPool`, or one with a null channel | The pool never posts anything at all |
| Empty `poll_creation_weekdays` | Polls never fire |
| No matches ingested in the lookahead window | Poll creation runs and finds nothing |

`check_pool` reports each as OK/WARN/FAIL and exits non-zero on FAIL, so it also works as a deploy gate.

**The checks themselves live in `predictions/readiness.py`, not in the command** — `check_pool` is a
renderer over `readiness.check_pool()`, and the admin's setup page and its **Ready?** changelist
column call the same function. A second copy of "is this pool ready" would be a copy that disagrees.
`readiness.check_environment()` covers the install-level prerequisites (any season with stages? has
the bot ever connected?), which is what the guided page opens with.

### Which NFL provider owns what

| | ESPN | nflverse |
|---|---|---|
| Schedule | ✅ forward window | ✅ whole season |
| In-progress scores | ✅ (`sync_nfl_live_games`, every ~2 min) | ❌ batch only |
| Final results | ✅ | ✅ (independent backstop) |
| Cadence | live loop + daily | a few times a day (`sync_nflverse_results`) |

`ingest_nflverse_nfl_matches` only writes status/scores when nflverse reports a game as played *and* the match is not already `FINISHED`, so it settles anything ESPN missed without re-firing the scoring signal for matches ESPN already closed.
